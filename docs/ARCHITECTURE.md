# Архитектура FieldOps

FieldOps остаётся одним приложением Next.js с PostgreSQL. Предметные модули позволяют развивать проект без дополнительных сервисов и зависимостей.

## Границы модулей

- `src/lib/domain.ts`: роли, права и переходы состояний, без подключения к базе.
- `src/lib/validation.ts`: проверка входных данных операций через Zod.
- `src/lib/queries/filters.ts`: нормализация URL-параметров, область видимости инцидентов и условия фильтрации. Модуль не создаёт Prisma Client.
- `src/lib/queries/incidents.ts`, `devices.ts`, `locations.ts`, `visits.ts`, `users.ts`: чтение соответствующих сущностей. Страницы и API импортируют нужный модуль напрямую.
- `src/lib/pagination.ts`: допустимые размеры страниц, разбор параметров, метаданные и ссылки. Не зависит от базы, Next.js или React.
- `src/lib/queries/page.ts`: выполнение подсчёта и выборки страницы в транзакции PostgreSQL с `RepeatableRead`.
- `src/lib/services/`: изменения данных с проверками прав, событий и транзакционности.
- `src/components/`: отображение данных и формы. Таблицы принимают типы записей, а не тип конкретной функции получения списка.
- `src/app/api/[...path]/route.ts`: HTTP-адаптер с проверкой сессии, `Origin`, JSON и преобразованием ошибок.

Правила прав и состояния должны сохраняться на сервере. Клиентские условия показа кнопок служат удобству интерфейса и не заменяют проверки сервисов. Для выездного инженера один и тот же фильтр назначения применяется к подсчёту инцидентов и выборке страницы.

## Реестры и пагинация

Страницы `/incidents` и `/equipment` используют серверную пагинацию. URL хранит фильтры, номер страницы `page` и размер `pageSize`; переходы сохраняют фильтры. Отправка формы фильтров или нового размера страницы начинается с первой страницы.

Допустимые размеры — `25`, `50`, `100`, по умолчанию `25`. Некорректный номер заменяется на `1`, некорректный размер — на `25`. При повторяющемся параметре используется первое значение. Номер за пределами выборки переводится на последнюю доступную страницу; пустая выборка имеет страницу `1` из `1`.

Общее количество и записи страницы читаются в одной транзакции `RepeatableRead`: параллельное добавление или удаление не рассогласует их внутри одного ответа. Инциденты сортируются по приоритету, времени создания и уникальному `id`, оборудование — по уникальному `assetTag`. При изменении базы между переходами содержимое страниц может сдвинуться: это обычное ограничение пагинации по смещению.

Dashboard получает показатели активных инцидентов отдельными запросами подсчёта, а для таблицы загружает только шесть записей. Глобальный поиск запрашивает до восьми результатов каждой категории непосредственно в базе.

## Совместимость API

Без `page` и `pageSize` существующие `GET /api/incidents`, `GET /api/devices` и `GET /api/locations/:id/devices` сохраняют ответ-массив и прежние ограничения: 200 инцидентов или 500 устройств.

При наличии хотя бы одного параметра пагинации эти маршруты возвращают объект:

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "pageSize": 25,
    "total": 0,
    "totalPages": 1
  }
}
```

Например, `GET /api/incidents?status=active&page=2&pageSize=25`. Для `/api/locations/:id/devices` объект из пути имеет приоритет над параметром `location`.

## Оборудование нового инцидента

Форма `/incidents` не получает общий реестр устройств с серверной страницы. Компонент `IncidentDeviceSelect` запрашивает `GET /api/locations/:id/device-options` для выбранного объекта. Ответ — массив полей `id`, `name`, `assetTag`, `ipAddress`, отсортированный по инвентарному номеру. Запрос выбирает все устройства этого объекта, кроме `RETIRED`; ограничение общего реестра в 500 записей не применяется. Неизвестный объект возвращает `404`, отключённый — `400`. Маршрут требует действующую сессию и возвращает `Cache-Control: no-store`.

При смене объекта React пересоздаёт только поле оборудования по `key`, сбрасывая выбранное устройство и состояние загрузки. Cleanup отменяет прежний запрос через `AbortController`; отменённый ответ не обновляет состояние. Название, симптомы и приоритет инцидента сохраняются. Ошибка загрузки имеет кнопку повторной попытки, пустой список — пояснение. Инцидент можно зарегистрировать без устройства. Серверная проверка принадлежности устройства объекту и его статуса сохраняется в `createIncident`.

## Проверки и следующий этап

Unit-тесты проверяют параметры, ссылки, фильтры и совместимость API. PostgreSQL-тесты создают 210 инцидентов и 505 устройств в отдельной базе `_test`, проверяют записи за прежними границами, сортировку, права и количество по фильтрам. Тестовые данные удаляются по уникальному идентификатору своей группы.

Следующий этап: пагинация личной работы, мониторинга и связанных списков в карточках. Для объектов с очень большим количеством устройств можно добавить поиск вариантов оборудования на сервере. Существующие ограниченные списки остаются явно отделены от пагинированных реестров и вариантов формы. Схема PostgreSQL на этом этапе не меняется.
